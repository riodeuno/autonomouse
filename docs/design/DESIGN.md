# autonomouse — living design doc

Your craft rules are the global Claude Code config (`~/.claude/CLAUDE.md`, loaded
automatically) and these skills: `software-design` (its `DESIGN-DOC.md` and
`AGENT-SYSTEMS.md`), `project-management` (its `PLANNING-PRS.md` and `LINEAR-ISSUES.md`).
This file holds only what is specific to autonomouse.

## What it is

A Kanban board that an agent works from and a human steers. Small, fully specified
cards; an orchestrator that wakes on a timer, works cards through sub-agents it watches
and manages while they run, and parks anything needing a human in one stack the human
watches.

## Glossary — the agreed language

| Term | Means | Rejected framings |
|---|---|---|
| Board | The whole Kanban: every project and every card, stored as JSON files in one directory | "Dashboard" (that is what the TUI shows, not the data) |
| Project | One goal tied to one git repository; owns a brief and cards | "Epic" (Jira vocabulary, nothing else here is Jira) |
| Brief | A project's own page, `projects/<slug>/brief.md` on the board: why the project exists, its goal sentence, its intent, who uses it and where, and how it works. The planner writes it with the human on the project's first planning thread, which `autonomouse project new` opens, before any card is planned | — |
| Card | One small unit of work with its goal, guardrails and verification, small enough for one worker in one run | "Task" (the task is what the card describes; the card is the board object), "Ticket", "Issue" (collides with GitHub issues) |
| Planning thread | A conversation between the human and a planner session, kept on the board and carried on Telegram or in the screen, that ends in cards; the human can join it live by resuming the planner's session (`autonomouse plan join`) | — |
| Stack | One of the six columns a card sits in: backlog, todo, in_progress, decision_needed, done, cancelled | "Column", "Lane", "Status" (the user's word is stack) |
| Decision | A question on a card that only a human can answer, or a step only the human can take; while one is open the card sits in decision_needed | "Blocker", "Question" (too broad — the agent asks itself questions all day) |
| Run | One wake of the orchestrator: lock, consult Jev, launch the orchestrator agent, record the outcome, exit | "Session" (collides with a Claude Code session; one run may start several) |
| Orchestrator | The Claude Code agent a run starts; picks up cards, spawns workers and manages them while they run (watches their notes, stops a stuck one and restarts its card or hands it back, starts a ready card whenever a slot is free, the cards it files mid-wake included), updates the board through the CLI | "Manager", "Supervisor" (the agreed name is orchestrator); "Dispatcher" (it manages its workers, it does not only start them) |
| Worker | A sub-agent the orchestrator spawns to do exactly one card in that card's worktree | "Sub-agent" (the generic mechanism; a worker is the role) |
| Handoff | The card's resume notes: worktree, branch, PR, last step done, next step, written before and after every worker action | "Checkpoint", "Progress" |
| Stuck signal | One of three signs, named in `docs/orchestrator/while-workers-run.md`, that a running worker will not reach a PR on its own: its next step repeats, review rounds or sub-agents climb without a PR, or its next step waits on something outside its card. `autonomouse card stuck <id>` prints the first that fires, with the words that fired it | "Timeout" (no signal is a time limit; a stuck worker is busy, not slow) |
| Jev | Typesafe AI's judgment model; code asks it typed questions (choice / noul / score) for run-level decisions; noul answers carry no confidence, so gates use choice | "Router", "Policy engine" |
| Behaviour log | Per run: how each agent behaved — its role, tool calls by name, cost and waits, and the run's board writes, stack moves and PR states — derived from the session transcripts and the board's card histories, never from shell commands; never what it built | "Audit log" (a card's history is the audit trail of board writes; this is the agents' conduct) |
| Daily review | A generated report of where humans had to decide and where humans sent work back, with the gap each points to | "Retro" |
| Installer | `install.sh` served beside the wheel; one curl installs the whole system on a fresh machine | — |
| Slot | One of the logged-in Chromes a browser pool (`browser.pool`, a second repository, [browsermaze](https://github.com/riodeuno/browsermaze)) holds, `browser.slots` of them; leased to one run's card at a time, over CDP, in place of a local browser | "Session" (collides with a Claude Code session); "Browser" (the pool runs several, not one) |
| Lease record | A run's own durable note of which slots it holds, under its state dir — not a board field, and not the pool's own bookkeeping, which `browsermaze lease`/`release` on the pool keep separately | "Claim" (collides with the board's project/card claim, a different lock on a different resource) |

## Boundaries — what owns what

```
 board/      the data model: card & project schemas, load/save (atomic), history, validation,
             the stuck signals of a running card (`board.stuck`, read only)
             exposes: Board, Project, Card, Stack, Decision, Handoff
 cli/        `autonomouse card|project|board …` — the agent's and scripts' only write path
             exposes: the command set (documented in the orchestrator prompt)
 tui/        the Textual app: read-only view + the few human actions (answer decision,
             move to cancelled). Planning is a conversation: a planner session asks the
             human one plain question at a time, on Telegram or in the screen, until goal,
             limits and test are agreed, then writes the cards through cli/ like everyone
             else; the human joins it live with `autonomouse plan join`
 run/        `autonomouse run`: lock, gather state, ask Jev, launch `claude -p`, log the run
             exposes: run(), the orchestrator prompt template
 behaviour/  the behaviour log: reads a run's session transcripts and card histories
             (read only), writes logs/<run-id>.jsonl and .summary.json beside the board;
             `autonomouse log`
 jev/        thin client over Typesafe's HTTP API; the question catalogue lives here
 browser/    thin SSH client over a browser pool's `browsermaze` command (a second
             repository of that name owns the pool's server side); lease/release a slot, read
             its logins, and the run's own lease-record file; `autonomouse browser`
 notify/     `autonomouse notify`: one function, one channel, Telegram, with no second sender
             or fallback beside it; `autonomouse notify poll` reads the human's replies
 review/     `autonomouse review daily`: reads history + decisions, writes the daily review;
             `autonomouse review behaviour`: reads the behaviour logs of a window of runs,
             the board's cards and its git history;
             `autonomouse review improve`: turns patterns that recur in the behaviour
             review into proposed instruction changes, as backlog cards
 setup/      install.sh, publish.sh, the pinned tool list
```

Dependencies flow downward only: tui, run, review depend on board and cli; run depends on
jev, notify, browser and behaviour; review also depends on behaviour, whose logs it reads;
behaviour depends on board; nothing depends on tui or setup.

Rules that live in code (`AGENT-SYSTEMS.md`'s division):
- Every board write goes through the CLI: schema validation, atomic write, history row. The
  agent never edits JSON by hand.
- One wake per machine, which superseded one run per project on 2026-10-16 (itself the successor of one run at a time, 2026-09-22, sys-d11): a run claims one project, and a wake that starts while any run is alive or stalled starts nothing. The next wake that finds none picks the smallest-`priority` project with work that is not done. A lock (`flock`, released by the kernel when its holder dies) covers only the decision — whether another wake lives, which projects are done, which project, which cards, the claim — so two wakes never decide at once. A second lock, the board commit lock in the board's git directory, is taken by every commit and push of the board (`autonomouse board commit`, the run controller), so a human's commit and a wake's never run at the same moment.
- An in_progress card whose run is dead is reclaimed by the next run and resumed from its handoff.
- Cards enter a run only when every card in depends_on is done.
- The spend ceiling (workers alive at once per run) is enforced in code above Jev's answer;
  no count caps runs per day, and the timer sets how often a run starts.
- A card enters in_progress only with a worktree path recorded — the handoff invariant.
- Notification fires on every transition into decision_needed, from code, not from the model.

Judgments that stay with a model:
- How to do the card, when to split it, when to ask a human (orchestrator / worker).
- Whether a running worker is stuck (code prints the signal that fired and the words
  that fired it, `autonomouse card stuck`; the orchestrator reads those words and the
  notes), which test or limit held it and how to loosen it, or which wait to hand its card
  back behind, and which tier a charter card needs (orchestrator).
- Run-level judgments with a fixed option set go to Jev: proceed or defer, which size per
  card (the size fixes its model and effort; `split` means larger than `m`), retry or
  escalate after a failure. Which cards run side by side is the orchestrator's (sys-i30),
  and the orchestrator starts a ready card whenever a slot is free.

## Decisions — why it is shaped this way

| Decision | Why |
|---|---|
| Python and Textual for the TUI and the whole tool | The system ships as a wheel installed by uv through `install.sh`. Textual is the one Python TUI library with CSS layout, themes, animation and mouse support. The board schema and CLI are language-neutral JSON; only `tui/` would be rewritten. |
| One JSON file per card and one per project, in one board directory outside any repository | A worker and a human can edit different cards at the same moment without clobbering, and diffs are per card. |
| The board directory is a git repository the CLI commits after every write | A free audit trail and undo; the daily review reads the history. |
| Board writes only through the CLI | Guarantees (schema, atomicity, history, notification) belong in code. |
| Jev is consulted from the run controller (code), not from inside the orchestrator agent | Its answers gate spend and scheduling; code applies them deterministically and logs them. |
| One run works one project, and one wake works at a time on a machine. The run claims the project (its run id on `project.json`), the orchestrator claims each card with `card start`, and a worker claims nothing. The orchestrator never writes code itself. A wake that starts while another wake is alive or stalled exits 3 and starts nothing, whichever project it would have taken, and `autonomouse run --project <slug>` forces a project only when none lives. `ceilings.workers_per_wake` applies to the one wake | The owner's rule (2026-10-16): "only one project can be worked on, on a machine at a time". A run's blast radius stays inside one repository, and two wakes never compete for the machine's CPU, `gh` rate limit or agent quota. A second wake that waited for the first (the 2026-09-26 waiting wake) was a second session spent on nothing, so it is gone. |
| Pick order: the smallest project `priority` that has work and is not done first, then card position within `todo`. Cards whose `depends_on` are not all `done` are skipped. A project whose last wake stopped or crashed comes first only among projects of equal priority | Which project gets picked is a fixed, readable rule. A project set to priority 0 is worked next even when another project is half done; when it has no work left for the agents the wake goes back to the other project (the owner's example, 2026-10-16: A was in progress, B is set to P0, the next wake works B, and once B completes it goes back to A). |
| A project is done when it says so. `done_at` on `project.json` is set by `autonomouse project done <slug>`, or by a wake at its start for a project with at least one card, every card `done` or `cancelled` and every `done` card's work on the default branch (the rule of `github base-branch`, `github.waiting_branch`: its PR merged into the default branch, or into a branch whose own PR merged, as the wake's shared branch `wake/<run id>` does only once its PR has merged; a card with no code has nothing to reach; `gh pr view`, one call per `done` card and one per distinct shared branch per wake, until the project is marked). A done project is not picked, swept or followed up; it is listed last and the board shows `DONE`. A new `todo` card on it clears `done_at`. When every project is done, the wake removes all three cron lines; a new `todo` card on a done project installs them again when they are missing | The owner's words (2026-10-16): "mark a project as done. Also, autonomouse should see if the PRs are merged and mark the project as done by itself"; "if there are no more projects, it stops. It also stops the cron." A card reaches `done` with its PR open, so nothing but the PR says the work shipped. Done is a mark on the project, not a count of its cards: the old `DONE` pill (no card in `todo` or `in_progress`) called a project with a PR waiting for review done. A PR merged into a wake's shared branch has not reached the default branch while that branch's own PR is open, and a project marked done would lose the sweep that reads that open PR (decided 2026-10-17). |
| No project-level lock beyond the run claim: two cards of one project run in separate worktrees on separate branches, and clashes surface at merge. No session outside the run (a human's helper session, the super-orchestrator) touches that project's worktrees or branches while the run is alive | A conflict fix by a second session in a run's own worktree raced the run's worker. |
| A claim records the Claude Code session id, the pid and the model and agent type that held it. Liveness is session-log freshness and process id. Takeover reads that session's own transcript; a session that crashed (never reached a clean end) holding fewer than `ceilings.resume_tokens` tokens is resumed with `claude -p --resume <session_id>`, and any other session restarts from the handoff notes. The run controller ends every session it starts cleanly: it waits for `claude -p` to exit, records its JSON result on the run, and a `SessionEnd` hook records the end reason | The agent's own logs are the truth about whether it is alive, and a slow-writing session must not be mistaken for a dead one. Resuming a big session re-reads its whole context on every turn, and the board already carries the work across sessions. |
| A card in `in_progress` carries a phase (writing, testing, ci, review), an iteration count (every test, fix, verify loop after a failed test, CI or review comment bumps it), the model and effort working it and when it was picked up | A human reading the board sees at a glance who is on a card, for how long, in which phase and in which loop. |
| The TUI shows one project at a time: a project list, then that project's board. Stacks run left to right: `decision_needed`, `todo`, `in_progress`, `done`, then off-screen to the right `backlog` and `cancelled`. The layout is fluid: columns keep a minimum card width and the board scrolls sideways when the terminal is narrower. Every action is reachable by keyboard; the mouse works but is never required | Decisions sit at the far left so the human's eye lands there first. |
| The installer works on a bare Ubuntu server: it installs uv, and uv installs its own Python; nothing assumes Python, node or git are present. It also installs the browser tooling the agent uses: Playwright with its Chromium, and two MCP servers that drive that Chromium, the Playwright MCP server (`@playwright/mcp`) and the Chrome DevTools MCP server (`chrome-devtools-mcp`), both registered in Claude Code's user-scope MCP config (`~/.claude.json`). It sets up no computer-use support | One command installs the whole system on a fresh machine. Nothing on the board needs computer use. |
| A missing capability is never worked around. When a job needs a board command that does not exist (say, delete a card), the agent creates a new card to add that command and leaves it for a separate worker; it does not hand-edit files or improvise | Every change to the board keeps going through the one write path, and each job stays small. |
| Jobs stay independent. When a job spins off a new card for a missing capability, it does not wait for it: it continues with a placeholder and finishes its own PR; the spun-off card is a separate PR. Whichever merges second pulls the default branch and resolves the clash. A job blocks on another only when continuing is truly impossible, and then it says so in its notes | Small, independent PRs merge in any order. |
| Every PR must leave main working on its own. A feature that needs several PRs lands behind a flag; the PR that turns it on goes in last | The default branch is always releasable. |
| Workers open PRs and never merge into the default branch. A pull request merges into the default branch only when the owner merges it, tells a super-orchestrator to merge it (`autonomouse github merge <slug> <pr>...`), or writes a project instruction (`orchestrator_instructions` or `worker_instructions` on `project.json`) that has an agent turn on GitHub auto-merge for it, under which GitHub merges it once the branch's protection rules are met; no other setting or flag merges anything, and nothing asks the owner on Telegram for a merge. The one other merge an agent makes is a worker's merge of its own green PR into the wake's shared branch `wake/<run id>`. A helper that needs a merge to be verified is verified against a scratch repository, never the project's default branch. `done` means the PR is open, green and verified. Each project records its repository, and may record a third-party tracker (Linear first), whose issue follows the PR's state as the `project-management` skill says, so a card in `done` can have an issue still In Progress | The owner decides what reaches the default branch, and an unattended merge on the owner's account is a decision only the owner makes. The owner's words (2026-10-17): "Setting something to auto-merge (squash) is different from actually merging it. Setting it to auto-merge (squash) just makes sure that I don't have to be around to merge them when all the checks pass and we have an approval." |
| Stacked branches: a card whose `depends_on` card is `done` but unmerged branches from that card's branch, and its PR targets that branch; when the base merges, the PR retargets the default branch | Otherwise every dependent card branches from a stale default branch. |
| The iteration count is no stop by count. A fifth failed attempt, or one cause failing two attempts, is the worker's cue to reassess, write what it sees and report; what follows (a larger model, a tester worker, a replan) is the orchestrator's decision, written on the card. A card that does not converge is a planning failure, not a decision: the orchestrator takes it back, re-reads the goal, limits and test, splits or rewrites the card and puts the parts back in `todo`. Only when it cannot see how to replan does it raise a decision | A route that keeps failing says the plan is wrong, not the goal. |
| Wakes per day, deferrals and iterations per card are not config keys. `wake.interval_hours` sets the cadence, and Jev's `wait_30m` is applied as `go`. The kill switch is the file `~/.config/autonomouse/PAUSE`. Workers per wake are eight by default, for speed: a wake exists to finish the project fast. `ceilings.workers_per_wake` is the width whether Jev is on or off; it is a spend, so a lower number is the human's decision (rules, item 10), never an agent's choice to be safe | A ceiling lowered "to be safe" slows the project with no gain. |
| Secrets live in `~/.config/autonomouse/.env` (mode 600), next to `config.toml`, and reach sessions through the environment only; no agent reads a secrets file's values, key names at most | An installed package has no source folder to hold the secrets file, and a secret outside every repository cannot be committed. |
| A worker owns only `phase`, `iteration`, `handoff` and `pr` on its own card and never commits the board. The orchestrator owns stacks, claims, new cards, splits, the run record and every board commit. Workers report missing capabilities; the orchestrator creates the cards | Two workers plus the orchestrator committing one git repository would collide. |
| A finished card with an unanswered question goes to `decision_needed`; the answer sends it to `done` when no more work is needed (`answer --done`) or to `todo` otherwise. A card re-entering `in_progress` keeps its worktree. A claim whose process lives but whose transcript is older than thirty minutes is `stalled`: left alone, reported | A finished-but-questioned card needs a way to reach `done`, and a live-but-silent session needs a state. |
| Every session the system runs, and the super-orchestrator session the human starts, uses `--dangerously-skip-permissions` | A prompt for permission in an unattended session is a hang. |
| `card start` makes the working folder itself, at `~/projects/autonomouse/worktrees/<project>/<card-id>` (override: `AUTONOMOUSE_WORKTREES`), instead of the orchestrator running `git worktree add` by hand. The next `autonomouse run`, whichever project it wakes for, removes a `done` card's folder once its PR has merged; the `worktree` field is never cleared, only the directory | The orchestrator needs no git shell-out before every card start, and the disk does not grow forever. |
| The agents' charters (`docs/`) ship inside the wheel as `autonomouse/docs/`. Every claude session autonomouse starts (the wake's orchestrator, the planner) runs in the folder that holds them, the repository checkout when the code runs from one, else the installed package (`autonomouse.home`), and its prompt names the charter's absolute path and the invocation that runs the board commands; the orchestrator passes that invocation on to each worker | An installed wheel has no repository checkout to read the charters from or start sessions in. |
| A red main never stalls a wake: a worker waits only for its own PR's checks and reports `blocked: main red on <test>` when the same test fails on main's latest commit; the orchestrator files the fix card, sends the blocked card back to `todo` depending on it, and starts the fix in the same wake | Waiting on a red main deadlocked a wake on its own project claim. |
| The orchestrator manages the wake, not only dispatches it. It loosens a limit, test criterion or wait that stops the project, with what and why in the card's history (rule 10). While workers run, its turn stays open and a Monitor (the Claude Code tool that turns a command's output lines into events) on the project's card files shows it every change to a running card's notes; it also counts each worker's sub-agents. On a stuck worker (the signals are in `docs/orchestrator/while-workers-run.md`) it stops the worker with TaskStop, sends the card to `todo` with a note naming what changed and why, rewrites its test with `card edit` and restarts it in the same wake, or hands the card back when the worker waits on something outside it. Every card it files mid-wake starts in that wake, up to `ceilings.workers_per_wake` | "Limits, targets and guardrails exist to serve the goal and save tokens; they are never hard blocks." The config's ceilings stay the human's spend decisions (rule 8). |
| An agent runs every step of a card's test; no step is the human's (rule 9). What an agent on this machine can do, the worker does: it sends a message through the bot, runs a command, drives a screen from a test, reads a file. What only the human can produce, such as a reply from the human's own Telegram account, is a fixture in the shape of the real input | "Why are the agents asking me to test? All the features are accessible from here. Send a Telegram message yourself and reply to it; mock what cannot be reached." |
| The stuck signals are code. `autonomouse card stuck <id> --agent-id <agentId>` prints the first of the three signals that fires on a running card, with the words that fired it, or nothing; the orchestrator runs it on each Monitor event and reads the quoted words and the notes before it stops a worker. A `card progress` history row's note carries the next step's text (`…, next_step: <text>`, last), so next steps can be compared. The text goes in the note, not in a new history key, because the card schema refuses unknown keys and an older installed copy would refuse every card a newer one wrote. The code knows the usual wordings only; a repeat in other words stays the orchestrator's reading | The signals were prose the orchestrator applied by reading notes, and a card kept only its latest next step, so a repeat left no trace. |
| A card's size is its tier. The size, `xs`, `s` or `m`, is the one marker of a card's effort and complexity, measured by the hardest decision inside its goal, not by its diff. The worker's model and reasoning effort follow from it by the config's `tiers` table, `xs` → `sonnet/xhigh`, `s` → `opus/xhigh`, `m` → `fable/high`; a card bigger than `m` is split, never started. Jev answers `size`, never `tier`: `autonomouse run` applies Jev's size when it names one of the sizes and the card's own size otherwise, records the size and its tier in the run record, and passes the tier to the orchestrator. The `sonnet/xhigh` floor is checked on the `tiers` table before a wake starts | The tier matches the task, neither cheap nor lavish: "delegate to capable orchestrators and workers; do not cheap out on their capabilities, do not underestimate the tasks, do not overestimate what the agents can do, and do not overspend." |
| The orchestrator owns the batch. `ceilings.workers_per_wake` is the number of workers alive at once, not the number of cards a wake picks: `autonomouse run` hands the orchestrator every ready card of the project, the first up to the ceiling to start at once and the rest to wait for a free slot, and the orchestrator starts a ready card whenever a slot is free. While workers run it splits, merges, cancels, files and rewrites cards as the project needs. Jev's per-card question is size alone, with `split` (larger than `m`) as one answer; Jev keeps `go` and `recover` | "The decision about conflict should be made by the orchestrator, not Jev. [...] Letting the system sit idle, waiting on one task is absolutely unacceptable." |
| Reshaping comes first and the wake's shared branch last. Before the orchestrator starts a card that shares a file with a card that is ready, `in_progress`, or `done` with its PR unmerged, it tries three moves on the cards still in `backlog` or `todo`: re-split, one owner, fold. Two cards that still share a file and do not depend on each other both start on the default branch, each with its own PR squash-merged on its own; when the first to merge leaves the other's PR conflicting, the conflict check reopens that card and its worker merges the default branch into its branch. Only for a short refactor in which several ready cards must each change one not-yet-split file does the orchestrator, after writing on each card why no move applied, make `wake/<run id>` with `autonomouse run interim <run id>`; each worker merges its own green PR into it, and the orchestrator opens the branch's one final PR at the wake's end. A card whose dependency is `done` with its PR unmerged still stacks on the branch `github base-branch` answers | "A card with no real dependency on another always gets its own small pull request, squash-merged straight into main on its own, never routed through a shared branch." The orchestrator, as the project's manager, decides the branch and merge mechanics for easy-to-review, small changes. Stacking many cards on other cards' branches left most open PRs conflicting with main. See "Cards that share a file" in `docs/orchestrator/conflict-check.md`. |
| Every code change ships with a test in the repository's own suite (rule 11): at least one test, pytest under `tests/` here, that fails on the base branch without the change, passes with it, and covers the behaviour the card's goal names; the card's `test` names that test file. A card that changes only docs or charters adds no suite test, and neither does a card with no code and no doc | "Let's always have a test for every change, otherwise I can't trust this autonomouse workflow." |
| A worker that does not follow its charter (`docs/worker.md`) gets a larger model on its next `card start`, which records it, or a tester worker the orchestrator spawns to run the card's test in the card's worktree and report what it saw; never a deterministic gate (a tool restriction, a hook or a check that rejects the worker's work), because a worker keeps every tool its card needs. The rule lives in `docs/orchestrator/tier-rubric.md` | "If the worker models are not smart enough to follow, we will increase the size of the model or have the orchestrator spawn a tester worker instead. A deterministic gate is not a solution." |
| A failed Jev request is never an answer. When the request fails, the wake runs as if Jev were off: `go`, each card's own size, and the same width as without Jev (`consult` in `src/autonomouse/jev/wake.py`). Jev skips a wake only with an answer that arrived | A failed request that fell back to skip started nothing for three wakes in a row. |
| A card builds what its goal names and nothing beside it: no second channel, no fallback, no option the card did not ask for. Something good to have is a new card (rule 2), not a line in the card's PR | Workers still kept a second sender and offered "both of the above" as an answer. |
| A step only the human can take is a decision on its card (the glossary's "Decision"), filed by the orchestrator with `card ask`. No agent relays in chat what the board can hold; the super-orchestrator points the human at the board | A step for the human relayed in chat was lost. |
| The system improves itself only through cards. `autonomouse review improve` (the boundaries line for review/) files each pattern that recurs in the behaviour review as a backlog card proposing the instruction change, with the review's rows as evidence. The system never edits a doc itself; the human moves the card to `todo` or cancels it | Deviations recurred across wakes before a human noticed. |
| Releases are semantic versions cut from main only. After lint and tests pass on main, CI uses the release command to cut a patch release; it skips already tagged and superseded commits. Minor and major releases remain explicit through `autonomouse release <minor|major>`. The release command bumps the version, prepends a `CHANGELOG.md` section of the PR titles merged since the previous tag, and pushes the commit with its tag `v<version>`. `autonomouse --version` prints the installed version, and every run record carries it in `version`, so the board shows which version each wake ran | A run's behaviour must be readable against the version that produced it. |
| A card is the end of a conversation. A request without goal, limits and test opens a planning thread; the planner asks one plain question at a time until they are agreed, then writes the cards; the orchestrator never reads threads (the boundaries line for tui/ and the glossary's "Planning thread") | Cards written from a one-line steer were rewritten and split. |

| Runs are scheduled by cron. `autonomouse timer install` writes three lines into the user's crontab, each marked `# autonomouse <job>`: the wake every `wake.interval_hours` (`0 */N * * *`), the morning review at 06:00 and `plan step` every five minutes; `remove` deletes only them. A wake that finds every project done calls `remove`, and a new `todo` card on a done project calls `install` when any line is missing (`rearm`). Each line's PATH is `$HOME/.local/bin`, then, at install time, the folder `shutil.which` finds each of `claude`, `uv`, `gh` and `git` in, each added once and only when not already in the list, then `/usr/local/bin:/usr/bin:/bin`; `install` fails, naming the tool, when one of the four is not on the installing user's PATH. Each line logs to the state folder. A fire missed while the machine is off is not run later | The same mechanism works on macOS later, and `install.sh` installs cron on a fresh machine. A cron-started wake's PATH is not a hand-started shell's, so a tool outside the fixed folders is invisible to it unless `install` adds its folder. |
| The clones and the worktrees live under `~/projects/autonomouse`: `repos/<slug>` and `worktrees/<project>/<card-id>`, beside `wake-reports` and `wake-logs`; `install.sh` makes the four folders, and `autonomouse project new` makes the first two when they are missing. | A project's brief is the first thing it gets: `autonomouse project new` ends by opening the project's brief thread and running the planner on it once; the planner asks the human one question at a time on Telegram, says the goal sentence and the intent sentence back for a yes, writes `brief.md` by hand in the format of `docs/board-schema.md`, and closes the thread with no card. Card planning starts with the human's next request. | A planner session's tier follows its kind. Before `plan step` starts or resumes a planner session, Jev judges it `complex`, `simple` or `collect-user-intent` (a session that only collects the human's intent), and the config's `planner` table maps the kind to the session's model and effort: `fable/high`, `opus/xhigh` and `opus/medium`. Jev only judges the kind; a Jev that is off, fails or answers below its floor gives `complex`, and so do the live sessions of `plan join` and `plan new`. The thread's `tiers` records each answer and tier | A planner is started every time there is a decision to be made; a session that only collects the user's intent needs less. |
| Workers borrow a logged-in browser from a browser pool when `browser.pool` names one, a local browser only when it does not, with no runtime fallback either way. Set, `autonomouse run` starts the orchestrator session, and every worker it spawns, with `--mcp-config` naming one Playwright MCP server per pool slot (`browser.slots`, 4 by default), `pool-1` up, over CDP, and `--strict-mcp-config`: no local Playwright or Chrome DevTools MCP tool exists that wake, whatever a card's test needs. `browser.pool` defaults to `""` (unset). A card leases a slot before it starts and releases it once its worker's run on it ends (`docs/orchestrator.md`, step 4/5/6); a lease a crashed or ended session left is released by `autonomouse run`'s own backstop. `autonomouse browser has-login <domain>` is a card's access check for a pool login the pool does not have yet; the pool's own machine, not this one, is where the human adds it | The pool's browsers carry real logins, so every slot is a credential: no fallback that could run a card's test in the wrong browser silently, and no card sharing a slot's login with another card at once. |
